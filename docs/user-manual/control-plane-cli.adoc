= Control-plane CLI

`messgr-control` is the operator CLI for everything short of the send path itself: producer
identity, tenant configuration, provider configuration, customer DEK pre-provisioning,
templates, partition lifecycle, and message-volume stats. Every subcommand below assumes a
tenant has already been provisioned (see the quickstart in the repository README).

== Producers

[source,bash]
----
cargo run --bin messgr-control -- producer register \
    --tenant-slug acme --name fraud-alerts \
    --cert-subject "CN=fraud-alerts.internal" \
    --owner-team fraud --contact fraud-oncall@example.com --actor operator@example.com
cargo run --bin messgr-control -- producer list --tenant-slug acme
cargo run --bin messgr-control -- producer disable --tenant-slug acme --name fraud-alerts \
    --actor operator@example.com
----

`producer register` registers an upstream system (fraud, statements, onboarding, ...) against a
tenant (DESIGN.md §4.9): it writes both the `producer` row in the tenant's own database and the
`producer_cert` mapping in the control database, in that order (a producer only in the tenant
database is inert; a `producer_cert` pointing at no producer is a worse, later failure). No send
path consumes this identity yet -- `messgr::producer::resolve` (below) is the first reader.

Re-running `register` with identical inputs for the same `--name` is a safe no-op. Re-running it
with different inputs for the same `--name`, or with a `--cert-subject` already bound to another
producer (in this tenant or a different one), is rejected with a non-zero exit.

`producer disable` sets **two** copies to disabled, control database first: `producer_cert.enabled`
(control) -- the column mTLS resolution actually reads, since resolution never opens a tenant
database -- and then `producer.enabled` (tenant) -- the source of truth `producer list` displays.
Neither row is ever deleted, so a disabled producer's certificate fails resolution with a
distinct, diagnosable "disabled" error instead of looking unregistered. Reversible by registering
the same `--name`/`--cert-subject` again (which never re-enables `producer_cert.enabled` -- only
`disable` and the initial `register` ever touch that column). Disabling an already-disabled
producer is a safe no-op.

Every `register`/`disable` attempt, including a rejected one, writes a `platform_audit` row
(`producer.register` / `producer.disable`).

== Tenant configuration

[source,bash]
----
cargo run --bin messgr-control -- tenant-config set --tenant-slug acme \
    --retention-years 7 --default-timezone Europe/London --default-locale en-GB \
    --quota-day-boundary-tz Europe/London \
    --actor operator@example.com
cargo run --bin messgr-control -- tenant-config show --tenant-slug acme
----

`tenant_config` (DESIGN.md §4.10) is a **singleton per tenant** -- one row, in the tenant's own
database, enforced by a `singleton boolean PRIMARY KEY` rather than by convention. A freshly
provisioned tenant has **no** row until `tenant-config set` is run at least once: several of
these fields (the quota day-boundary timezone) have no platform-wide
default DESIGN.md has settled on, so there is nothing sensible to seed automatically.

`set` is a plain upsert -- safe to re-run. Its outcome is `created` (no prior row), `updated`
(a prior row existed with different values), or `idempotent` (identical to what's already
there); every call, including a rejected one against an unknown `--tenant-slug`, writes a
`tenant_config.set` `platform_audit` row. `--schedule-horizon-days` and `--verification-mode`
are optional, defaulting to DESIGN.md's own `90`/`observe`. This ticket (T-007) scopes the
table to the six fields above; two further tunables were added later and are each documented at
their own point of use rather than here -- `--kill-switch-release-rate` (kill-switches.adoc,
"Releasing a switch") and `--reconcile-attempts-cap` ("Orphan-event reconciliation" below).
`display_name` and the `oidc_*` columns from DESIGN.md's full §4.10 table arrive later, when a
ticket actually reads them (a future OIDC ticket, not yet filed).

NOTE: A tenant needs a `tenant_config` row before `messgr-ingest` will serve any request against
it -- the tenant registry rejects a send with "tenant has no tenant_config row" otherwise. Run
`tenant-config set` right after provisioning, before exercising the ingest walkthrough.

== Customer projection

`messgr` is never the system of record for customer data -- `customer`, `customer_external_id`,
`customer_address`, and `customer_alias` (DESIGN.md §4.6, `T-015`) are a narrow, read-only
projection, held only to resolve _who to send to right now_: an id, a locale, a timezone, and a
handful of contact points, nothing else. There is no CLI surface for these tables; every write
to them happens inside `messgr-ingest`'s resolution path.

`messgr-ingest` resolves every send to a `customer_id` + `address_id` one of three ways
(DESIGN.md §4.7):

* **`customer_id` supplied** -- used directly, after alias expansion (`customer_alias` redirects a
  retired id from a master-system merge to its current one).
* **`external_id` + `external_id_system` supplied** -- resolved via `customer_external_id`.
* **Neither supplied** -- resolved via `destination`'s keyed HMAC against currently-active
  `customer_address` rows.

**Resolution never rejects a send.** Whichever of the three finds nothing mints a _provisional_
customer (and, for address-only resolution, a provisional address) instead -- cheap, thin rows
that get a DEK like any other customer and are reconciled into a real identity later by the event
feed, through the same `customer_alias` merge machinery. A blocked OTP is a worse outcome than a
missing timeline entry, so nothing here ever returns anything but a resolved id -- including a
`customer_id`/`external_id` whose destination turns out to already be active under a _different_
customer: resolution resolves to that other customer rather than reject the send (`T-018`).

One piece of the design is explicitly not built yet: the **event feed** that keeps the
projection current from the master system (create/update/merge events; build-order step 10).
Until the feed exists, every non-provisional row in these tables was put there by a previous
resolution, not by upstream master data.

== Partition lifecycle

[source,bash]
----
just tablespace-init   # once per Postgres instance -- creates the messgr_cold tablespace
cargo run --bin messgr-control -- partition-lifecycle run --tenant-slug acme
----

`comms_request` and `comms_event` (DESIGN.md §4.1, T-009) are partitioned by month. This
command (T-014) keeps them self-managing, in one run: ensures the current and next month's
partitions exist, moves partitions older than 18 months (fixed platform-wide, §7.5) to the
`messgr_cold` tablespace (created once per cluster by `just tablespace-init`, not by this
command -- tablespaces are shared across every database in the instance), and detaches + drops
partitions past the tenant's `tenant_config.retention_years` boundary. **If the tenant has no
`tenant_config` row, the drop step is skipped entirely** -- printed as `retention: skipped
(tenant_config not set)` -- rather than assuming a default retention on a bank's ledger data.
Safe to re-run; meant to be invoked on a schedule (cron/systemd timer), not run continuously --
this binary does not daemonize.

== Idempotency sweep

[source,bash]
----
cargo run --bin messgr-control -- idempotency-sweep run --tenant-slug acme
----

`idempotency` (DESIGN.md §4.3) rows are retained 30 days from the write that created them, then
swept. This command (T-029) deletes every row whose `expires_at` is at or before the time it
runs, for one tenant. No Vault/Transit dependency -- the table holds no PII. Safe to re-run;
meant to be invoked on a schedule (cron/systemd timer), not run continuously -- this binary does
not daemonize.

== Orphan-event reconciliation

[source,bash]
----
cargo run --bin messgr-control -- orphan-reconcile run --tenant-slug acme
----

A delivery-receipt webhook that arrives before, or without, a matching `comms_request` is parked
in `orphan_event` rather than discarded (DESIGN.md §4.4/§10). This command (T-030) re-attempts
matching each pending row's `provider_ref` against `comms_event.provider_ref` rows written since:
a match is encrypted under the matched customer's DEK and promoted into a real `comms_event` row,
advancing `comms_request.final_status` without ever regressing an already-more-final status; a row
with no match, or whose `event_type` is outside the set DESIGN.md §4.4 documents (never checked
against `comms_event` at all in that case), has its `reconcile_attempts` counter incremented and
is deleted once that counter reaches `tenant_config.reconcile_attempts_cap` (default 5; set with
`messgr-control tenant-config set --reconcile-attempts-cap <n> ...`), which also emits a
`tracing::warn!` naming the tenant, orphan id, provider_ref, and event_type. Unlike idempotency-sweep and
partition-lifecycle, this command does connect to Vault -- promotion is the payload's first write under a customer scope. Safe to re-run;
meant to be invoked on a schedule (cron/systemd timer), not run continuously -- this binary does
not daemonize.

== Webhook receipt promotion

[source,bash]
----
cargo run --bin messgr-control -- webhook-promote run --tenant-slug acme
----

`messgr-webhook` (DESIGN.md §10, T-047) writes every verified receipt it receives into
`webhook_receipt_staging`, unencrypted -- it holds no tenant's Transit credentials, so encryption
happens here instead. This command matches each pending row's `provider_ref` against
`comms_event.provider_ref`, exactly as orphan-event reconciliation does above (reusing the same
`find_match` query and the same recognized-`event_type` guard): a match is encrypted under the
matched customer's DEK and promoted into a real `comms_event` row; a row with no match yet is
handed to `orphan_event` for the orphan-event reconciliation command above to pick up on its own
schedule. A promoted `bounced` or `complaint` event also upserts a `suppression` row for the
destination (see "Suppression list" below) -- the automatic half of suppression population T-038
deferred to this ticket; `review_at` defaults to one year and the upsert never shortens an
existing entry. Like orphan-event reconciliation, this command does connect to Vault. Safe to re-run;
meant to be invoked on a schedule (cron/systemd timer) -- start at every 1 minute, the latency
bound between "provider called the webhook" and "status visible"; tighten it here first if that
is ever too slow, before reaching for a listener process -- not run continuously; this binary
does not daemonize.

== Message stats

[source,bash]
----
cargo run --bin messgr-control -- stats --tenant-slug acme
cargo run --bin messgr-control -- stats --tenant-slug acme --since 2026-08-01
----

Per-tenant message-volume counts, by channel (`sms`, `email` only -- `whatsapp` rows are never
included) and by `comms_request.final_status`, read directly with no join to `outbox` or
`comms_event` (T-028). `--since` restricts to requests created on or after that UTC date;
omitting it reports all-time counts.

Output is one `total=` line per channel followed by one `status=`/`count=` line per distinct
status seen for that channel. A `NULL final_status` (still in flight) is reported as
`status=pending`. As of this writing the other values the dispatcher actually writes are
`sent`, `failed`, `expired`, and `discarded` (a row swept by an engaged kill switch --
`src/dispatcher/drain.rs`'s `write_discarded`) -- DESIGN.md §4.4 documents a larger eventual
vocabulary (`delivered`, `bounced`, `cancelled`, `suppressed_consent`, `suppressed_list`,
`unverified_address`). `delivered`/`bounced` now appear too, once `webhook-promote` (T-047,
above) has run against a matching receipt; the rest depend on gate-chain wiring, and this
command reports them the moment the dispatcher starts writing them, with no code change
required here.

This reads Postgres directly, the same trust boundary as every other `messgr-control`
subcommand (whoever can run the binary already has database access) -- no new authentication
surface, and no message content (`payload_ciphertext`, `destination_ciphertext`) is ever read.

== Provider configuration

[source,bash]
----
cargo run --bin messgr-control -- provider-config set --tenant-slug acme \
    --channel sms --priority 1 --provider generic-http \
    --credential-path secret/data/acme/sms --rate-limit-per-sec 10 \
    --actor operator@example.com
cargo run --bin messgr-control -- provider-config list --tenant-slug acme --channel sms
----

`provider_config` (DESIGN.md §4.10, §12.1) is an **ordered list per channel**, in the tenant's
own database, keyed by `(channel, priority)` -- even at length 1, so later multi-provider
failover is a config change rather than a schema migration. `set` is a plain upsert on one
`(channel, priority)` row at a time -- safe to re-run, with the same `created`/`updated`/
`idempotent` outcome and `platform_audit` trail as `tenant-config set`. `list` prints a
channel's rows in failover order (lowest `priority` first).

No real vendor is wired up yet -- `provider` is a free-text label, and `HttpSender` (the first
`Sender` implementation) speaks a small JSON-over-HTTP contract of this codebase's own design,
proven against a local mock server rather than a committed vendor's API (DESIGN.md's own
"provider selection" question, Still Open #5, stays open). `rate_limit_per_sec` is stored but not
yet read by anything -- rate-limit enforcement is a later ticket's work.

`credential_path` is now read by `messgr-dispatcher` at startup (DESIGN.md §13, T-023):
`messgr-control` never touches the secret value itself, only this pointer to it. It is the raw
Vault HTTP-API KV v2 form `<mount>/data/<path>` -- e.g. `secret/data/acme/sms`, the tenant's own
prefix under Vault's default `secret/` KV v2 mount -- and the secret at that path must be a JSON
object with one field, `{"api_key": "..."}`, written out-of-band by an operator (`vault kv put`
or the raw HTTP API) after `provider-config set` stores the pointer:

[source,bash]
----
curl -sf --header "X-Vault-Token: $VAULT_TOKEN" --request POST \
    --data '{"data":{"api_key":"..."}}' \
    "$VAULT_ADDR/v1/secret/data/acme/sms"
----

Only the highest-priority row per channel is resolved at startup -- failover-on-priority is
resolved out of scope for now (this ticket's own Description item 4); the ordered-list schema
exists so a second provider is a config change later, not something this ticket wires up.

`messgr-sms-sender` (T-052) is a second reader with different behaviour: it walks the whole
`sms` list, in priority order, synchronously within each OTP send, trying the next row
immediately on failure -- a live customer is waiting, so this is deliberately smaller than
`messgr-dispatcher`'s own future circuit-breaker/half-open-probe design for queued traffic. See
"messgr-sms-sender" below.

== Suppression list

[source,bash]
----
cargo run --bin messgr-control -- suppression add --tenant-slug acme \
    --destination +15550100 --reason hard_bounce \
    --review-at 2027-01-01T00:00:00Z --actor operator@example.com
cargo run --bin messgr-control -- suppression list --tenant-slug acme
cargo run --bin messgr-control -- suppression remove --tenant-slug acme \
    --destination +15550100 --actor operator@example.com
----

`suppression` (DESIGN.md §5, §4.4, T-038) blocks every further send to a destination that hard
bounced, complained, or is under a regulatory hold, checked by `messgr-dispatcher` at send time
for every message class with no exemption. `add` computes `destination_hmac` from the raw
`--destination` itself (via the tenant's own pepper, exactly as `messgr-ingest` does) and
upserts a row keyed on that hash -- `--destination` is never stored or logged. `--reason` is a
closed vocabulary: `hard_bounce`, `complaint`, or `regulatory_hold`. `--review-at` is a
mandatory RFC 3339 timestamp; the entry blocks only while it is still in the future, and once it
passes the gate query simply stops matching -- no sweep job runs to clean it up. `add` is not the
only writer of this table -- `webhook-promote` (above) also upserts a row automatically for a
promoted `bounced`/`complaint` receipt, with a one-year `review_at` default and the same
never-shortens guard.

`remove` is exactly "move `review_at` to now": the same mechanism as letting an entry expire
naturally, so there is no separate "removed" state. It is rejected if the destination has no
currently-active entry (already expired, or never suppressed).

`list` prints every entry for a tenant with `destination_hmac` hex-encoded and a computed
`status` (`active` or `expired`) -- the HMAC is one-way, so there is nothing to reverse it back
to the original address.

== Consent

[source,bash]
----
cargo run --bin messgr-control -- consent set --tenant-slug acme \
    --destination +15550100 --channel sms --class marketing \
    --opted-in true --source web_form --actor operator@example.com
----

`consent` (DESIGN.md §5, §4.4, T-037) records a customer's opt-in/opt-out for one message class
on a destination, checked by `messgr-dispatcher`'s consent gate at send time for `marketing`
messages only -- `transactional` never requires opt-in. `set` requires a pre-existing, active
`customer_address` for the destination (resolved the same way `messgr-ingest` resolves one, via
the tenant's own pepper) and is rejected otherwise -- it never mints an address, unlike ingest's
own resolution path; record consent after the customer's first message, or via whatever
event-feed consumer eventually lands (build-order step 10). `--class` is closed to
`transactional`/`marketing`. `--opted-in` is a plain `true`/`false`. `--source` is free-text
evidence of where the choice was captured (e.g. `web_form`, `ivr_call`, `branch_visit`,
`sms_stop_reply`) -- not customer-supplied content. Re-running with identical inputs is
idempotent, same `created`/`updated`/`idempotent` outcome and `platform_audit` trail as
`suppression add`/`tenant-config set`.

== Producer quotas

[source,bash]
----
cargo run --bin messgr-control -- producer-quota set --tenant-slug acme \
    --producer-name marketing-service --channel sms --class marketing \
    --per-minute 50 --per-day 5000 --enforcement hard --actor operator@example.com
cargo run --bin messgr-control -- producer-quota list --tenant-slug acme
cargo run --bin messgr-control -- producer-quota override-add --tenant-slug acme \
    --producer-name marketing-service --channel sms --class marketing \
    --per-day 20000 --valid-from 2027-01-01T00:00:00Z --valid-to 2027-01-02T00:00:00Z \
    --approved-by ops-lead --reason "New Year campaign day" --actor operator@example.com
cargo run --bin messgr-control -- producer-quota override-list --tenant-slug acme
----

`producer-quota` (DESIGN.md §5.1, T-042) sets a producer's per-minute burst and per-day total
send quota for one `(channel, class)`, enforced by `messgr-dispatcher`'s quota gate at dispatch
time -- never at ingest. `--channel` is closed to `sms`/`email`/`whatsapp`; `--class` is closed
to `marketing`/`transactional` -- **`auth` is never a legal `--class` value here**: auth traffic
is exempt from quota but always counted unconditionally, so a quota row for it would be
meaningless. `--per-minute`/`--per-day` are each optional; omitting either means unlimited on
that window. `--enforcement` is closed to `hard`/`soft`, with one restriction: `hard` is
rejected for `class = transactional` (AGENTS.md hard invariant 5 -- quota must never be able to
block transactional traffic); `marketing` may be `hard` or `soft`. Re-running `set` with
identical inputs is idempotent, same `created`/`updated`/`idempotent` outcome and
`platform_audit` trail as `suppression add`/`consent set`.

`override-add` raises `--per-day` only for a time-boxed window (`--valid-from`/`--valid-to`,
both mandatory RFC 3339 timestamps) -- it never touches `enforcement`, which is always inherited
from the base `producer-quota set` row. It is rejected for `class = auth` (same reason as
`set`), or if `--valid-to` is not after `--valid-from`. `override-list` prints every override
for a tenant, newest `--valid-from` first.

== Quiet hours

[source,bash]
----
cargo run --bin messgr-control -- quiet-hours set --tenant-slug acme \
    --start-local 22:00 --end-local 07:00 --actor operator@example.com

cargo run --bin messgr-control -- quiet-hours show --tenant-slug acme
----

`quiet-hours` (DESIGN.md §5, §6.1, T-043) sets or shows the tenant's institution-wide quiet-hours
window, enforced by `messgr-dispatcher`'s quiet-hours gate at send time: a message due inside the
window reschedules to window end plus up to 30 minutes of uniform jitter instead of sending.
`--start-local`/`--end-local` take `HH:MM` in 24-hour time; a window may wrap midnight (e.g.
`--start-local 22:00 --end-local 07:00`). Only the institution-wide default is settable today --
there is no `--scope`/`--scope-key` flag, even though the underlying schema supports per-segment
and per-region windows; see `05-send-timing.md`'s §6.1 correction note for why those scopes are
currently unreachable. Re-running `set` with identical inputs is idempotent, same
`created`/`updated`/`idempotent` outcome and `platform_audit` trail as `consent set`/`suppression
add`. A change takes effect on `messgr-dispatcher`'s next restart -- the window is read once at
startup, not hot-reloaded.

== Customer DEK pre-provisioning

[source,bash]
----
cargo run --bin messgr-control -- customer-dek pre-provision --tenant-slug acme \
    --customer-id 11111111-1111-1111-1111-111111111111 \
    --customer-id 22222222-2222-2222-2222-222222222222 \
    --actor operator@example.com
----

`customer-dek pre-provision` (DESIGN.md §7.6) ensures each given customer id has a `customer_dek`
row, minting a fresh Vault Transit datakey for whichever don't -- so a sealed or unreachable Vault
doesn't block a new customer's first message. It takes **explicit customer ids, not a live
customer base**: the customer projection (DESIGN.md §4.6, "Customer projection" above) has no
event feed yet (build-order step 10), so there is no live upstream source for this command to
query on its own. Wiring an automatic trigger from the real customer base is deferred to
whichever future ticket adds that feed.

Safe to re-run: identical ids report `already_existed` instead of minting a second DEK. The same
lifecycle also has a lazy path (`customer_dek::lifecycle::get_or_create_dek`) that future
ingest/dispatcher code calls on a customer's first message -- no CLI surface for that path, since
it has no operator action to trigger.

Every payload/destination this eventually encrypts uses a **bounded, zeroizing, TTL cache**
(`key_cache::KeyCache`) of unwrapped DEKs, so steady-state sending makes no Vault calls once a
customer's DEK is warm -- Vault is only on the path for a cache miss or pre-provisioning.

== Templates

[source,bash]
----
cargo run --bin messgr-control -- template approve --tenant-slug acme \
    --template-id balance-alert --version 1 --channel sms --locale en-GB \
    --body-file body.txt --actor operator@example.com
cargo run --bin messgr-control -- template show --tenant-slug acme \
    --template-id balance-alert --version 1 --locale en-GB
cargo run --bin messgr-control -- template list --tenant-slug acme --template-id balance-alert
cargo run --bin messgr-control -- template render --tenant-slug acme \
    --template-id balance-alert --version 1 --locale en-GB \
    --var name=Jordan --var "balance=£120.00"
----

`template` (DESIGN.md §4.4) rows are **immutable once approved** -- `approve` is the only way a
row is ever written, and it always stamps `approved_by`/`approved_at`; there is no draft state
and no `update`. A content change is always a new `--version`: re-`approve`-ing an existing
`(template_id, version, locale)` is rejected, not overwritten.

Bodies use literal `{{key}}` placeholders (whitespace inside the braces is trimmed, so
`{{ key }}` also matches), substituted by `template render` or by `messgr-ingest`'s own send
path. A key the body references but the caller doesn't supply is a **hard render error** -- a
bank must not send customer-facing content with an unsubstituted placeholder -- never sent as
literal `{{key}}` text or blanked out.

Every `approve` attempt, including a rejected one, writes a `template.approve` `platform_audit`
row. This is the bare operator-driven surface, matching `producer`/`tenant-config` -- the audited,
role-gated admin approval workflow (§11.1, §11.3) is `T-042`'s scope, not this one's.

NOTE: The `(template_id, version, locale)` primary key does not include `channel` -- approving
the same `template_id`/`version`/`locale` for two different channels collides. Give each channel
its own version (or its own `template_id`) if you need channel-specific bodies at the same
nominal version.

== Offboarding

[source,bash]
----
cargo run --bin messgr-control -- offboard-destroy \
    --tenant-slug acme --confirm-slug acme --actor operator@example.com
----

`offboard-destroy` (DESIGN.md §7.7, T-059) fully terminates a tenant: its Vault Transit key,
mount, ACL policy, and AppRole are destroyed, its database is dropped
(`DROP DATABASE ... WITH (FORCE)`), and its `tenant` row is marked `offboarding_destroy` -- the
inverse of provisioning. Vault is destroyed first, so the tenant's data becomes permanently
unreadable *immediately*, before the database is touched.

WARNING: This is immediate and, in practice, irreversible -- there is no undo. `--confirm-slug`
must repeat `--tenant-slug` back exactly, so a destructive operation is never one flag away from
running by accident. The tenant's data is unreadable the instant this command returns, but a
database backup taken before the run still holds the wrapped keys it was encrypted under until
that backup itself ages out of retention (§7.3) -- "unreadable now" is not "purged from every
backup now".

Safe to re-run against an already-destroyed tenant: every step tolerates its target already being
gone.

**Terminate-and-archive** -- retaining the database and key for the tenant's remaining retention
period, with producers/UI disabled and dispatchers stopped, converting to destroy after an
explicit end date -- is not built. §7.7 leaves it pending a pricing decision (design-doc still-open
item #13); `offboard-destroy` only ever destroys.
