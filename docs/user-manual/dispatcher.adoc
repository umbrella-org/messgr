= messgr-dispatcher

`messgr-dispatcher` (`T-013`) is the first real send path: a per-channel claim loop (`SKIP
LOCKED` leases, `LISTEN`/`NOTIFY` wakeup via a trigger on `outbox` inserts with a 1s poll
fallback) that calls the `Sender` trait (`T-012`) and writes exactly one `comms_event` row plus
one `comms_request.final_status` update per outbox row, deleting it on completion (DESIGN.md
§4.1, §4.2, §4.4, §9). One process per tenant; leader election (`pg_try_advisory_lock`-based HA)
is still a later build-order step.

`T-021` adds retry with backoff for retryable send failures (DESIGN.md §2.4 step 6, §12.2): a
5xx-equivalent provider status or a transport-level failure clears the row's lease and
reschedules `next_attempt_at` with exponential backoff and jitter (30s base, doubling, capped at
30 minutes) rather than failing on the first attempt, up to 8 attempts before it finally
terminal-fails. A 4xx-equivalent provider rejection still fails immediately -- it is a
permanent rejection, not a transient one. A transient `repo::claim` database error now retries
(logged, 1s delay) instead of panicking that channel's task. `messgr-dispatcher` also sweeps
every stale lease for its tenant at startup, before any claim loop runs, so a row left leased by
a killed-and-restarted process (a crash before any terminal write or reschedule ran) is
reclaimed immediately rather than staying stuck -- safe only because exactly one dispatcher
instance runs per tenant today; this sweep is revisited once leader election ships and a
restart is no longer guaranteed to be the sole claimant.

`T-016` adds kill-switch enforcement (DESIGN.md §5.2): a shared, in-process cache of currently
engaged switches, refreshed by a dedicated `LISTEN kill_switch` connection with a 30-second poll
fallback, is checked *before* each claim -- a matching row is excluded from the candidate set
entirely, never leased and gate-blocked. Releasing a `hold` switch ramps its backlog back in at
`tenant_config.kill_switch_release_rate` rows/second per channel rather than all at once; a row
whose `expires_at` has already passed by the time it's drained is written `expired`, not sent.
Engaging a `discard` switch immediately terminal-writes (`discarded`) everything it already
matches. See "Kill switches" for the operator runbook.

`T-038` adds the suppression gate (DESIGN.md §5): the first in-line gate check this send path
runs (kill switches, above, are checked before a row is even claimed, not inside this path),
before any decrypt, so a blocked send never spends a DEK fetch. It runs unconditionally for
every message class -- no exemption, unlike verification/consent below. A destination present
in `suppression` with `review_at` still in the future terminal-writes a `suppressed_list` event
instead of sending; an entry whose `review_at` has already passed no longer blocks -- the gate
query itself stops matching it, no sweep job needed. See "Suppression list" (control-plane CLI)
for managing entries.

`T-036` adds the verification gate (DESIGN.md §5), checked next: for `transactional` and
`marketing` class messages, the dispatcher checks `customer_address.verified_at` before
decrypting. Per-tenant `tenant_config.verification_mode` controls the outcome for an unverified
address: `enforce` blocks the send and writes a terminal `unverified_address` event/status, the
same as `expired`/`discarded`; `observe` (the default) records the same `unverified_address`
event non-terminally and lets the send proceed anyway, so an address that never gets
verification data still gets sent and the gap stays visible in the ledger rather than silently
blocking or silently passing. `auth` class messages skip this gate entirely -- consistent with
AGENTS.md hard invariant 1, though in practice `auth` never reaches the outbox at all (T-011
decision 3). The mode is read once at dispatcher startup; changing
`tenant_config.verification_mode` takes effect on the next restart, not live.

Requires `DISPATCHER_TENANT_SLUG` (which tenant this process serves), `VAULT_ROLE_ID` /
`VAULT_WRAPPED_SECRET_ID` (this tenant's own AppRole -- printed by `just provision` on a fresh
provisioning run), and, per channel in `DISPATCHER_CHANNELS` (default `sms`),
`DISPATCHER_<CHANNEL>_BASE_URL` -- a dev stand-in `Sender` endpoint, since `provider_config` has
no `base_url` column. The credential itself comes from `provider_config.credential_path` via
Vault KV (T-023) -- no `DISPATCHER_<CHANNEL>_API_KEY` env var anymore. `DISPATCHER_HEALTH_LISTEN_ADDR`
(default `0.0.0.0:8081` -- distinct from `messgr-ingest`'s own `INGEST_HEALTH_LISTEN_ADDR`
default of `0.0.0.0:8080`, so the two can run on the same host unmodified; `T-032`) binds a
plain listener serving only `GET /healthz` -- a bare `200` for an orchestrator/LB liveness
probe; this binary otherwise has no HTTP surface at all.
Seed the channel credential locally the same way `scripts/e2e.sh` does:

[source,bash]
----
curl -sf --header "X-Vault-Token: messgr-dev-root-token" --request POST \
    --data '{"data":{"api_key":"dev-key"}}' \
    "http://localhost:8200/v1/secret/data/acme/sms"
----

With a tenant provisioned (its `vault_wrapped_secret_id` copied from that output), configured
(including `provider-config set` pointing at the KV path above), a credential seeded at that
path, and a message already sitting in its `outbox` (the `messgr-ingest` walkthrough above):

[source,bash]
----
DISPATCHER_TENANT_SLUG=acme DISPATCHER_CHANNELS=sms \
DISPATCHER_SMS_BASE_URL=http://localhost:9091 \
VAULT_ROLE_ID=<from just provision> VAULT_WRAPPED_SECRET_ID=<from just provision> \
just dispatcher-run
----

Within about a second (the poll fallback; a `NOTIFY` on insert makes it near-instant),
`comms_request.final_status` moves to `sent` on success. On a 4xx-equivalent provider rejection
it moves to `failed` immediately; on a 5xx-equivalent status or an unreachable provider the row
instead stays queued with `next_attempt_at` pushed forward by backoff, retried up to 8 times
before `final_status` finally becomes `failed`. Either terminal outcome writes exactly one
matching `comms_event` row and removes the `outbox` row.

TIP: `VAULT_WRAPPED_SECRET_ID` is single-use (10-minute TTL) -- unwrapping it a second time (e.g.
restarting the dispatcher against a wrapped id that was already consumed) fails. Re-provisioning
an already-active tenant does not mint a new one; see the credential-rotation note in the
repository README's provisioning walkthrough. For a repeatable local dev loop, start
`messgr-dispatcher` once per fresh provision and leave it running rather than restarting it.
