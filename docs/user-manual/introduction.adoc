= Introduction

{product} is a centralized communications orchestration system and audit ledger for a bank:
every SMS, email, and WhatsApp message sent to a customer passes through it, is recorded, and
is queryable through one API and UI. The full design — data model, gate chain, PII handling,
tenancy — is recorded in `DESIGN.md` at the root of the repository; this manual documents how
to operate what has actually been built against that design.

== Status

{product} is a design-driven, from-scratch rebuild. Feature work is tracked as tickets against
`DESIGN.md` (see `tickets/BOARD.md`), and only part of the design is implemented so far. Three
binaries exist today: `messgr-control` (the control-plane CLI — tenant provisioning, the
producer registry, tenant/provider configuration, templates, and a dev-only internal PKI),
`messgr-ingest` (`POST /comms`, the first end-to-end send path), and `messgr-dispatcher` (the
per-tenant claim loop that actually calls a provider). Verification (`T-036`), consent
(`T-037`), suppression (`T-038`), and producer quota (`T-042`) are all enforced today, at
dispatch time; kill switches (`T-016`) are enforced at both ingest and dispatch. Only the query
API/UI remain — a later ticket — see "messgr-dispatcher".

Each binary also accepts a `version` subcommand that prints its name and version, then exits
without reading any configuration (`messgr-control version`, `messgr-dispatcher version`,
`messgr-ingest version` → `messgr-control 0.1.0`, etc.).

== Tenancy

{product} is multi-tenant: each tenant gets its own database, and a shared control database
holds the tenant registry, producer-certificate mappings, and platform audit trail.
`messgr-control provision` creates a tenant's database, applies its migrations, registers it in
the control database, and provisions the tenant's own HashiCorp Vault Transit mount, key, ACL
policy, and AppRole for per-customer data-encryption keys.

=== Regions

Each region is an independent deployment: its own control database, Vault cluster, Postgres,
and binaries. Every tenant belongs to exactly one region, and nothing in one region reads from or
writes to another. Every binary requires `MESSGR_REGION`, which names the region it serves (for
example `eu`). The region is enforced at two points:

* *On boot.* Every binary, and every `messgr-control` subcommand except `migrate`, checks that
  each tenant in its control database carries its own `MESSGR_REGION`. If one doesn't, the
  process refuses to start with a `region mismatch` panic that names both regions. This catches
  a binary accidentally pointed at another region's control database, which would otherwise
  serve that region's tenants without any error.
* *On provision.* `messgr-control provision --region` must equal `MESSGR_REGION`. A tenant row
  labelled for another region is refused before it is written.

For local work, `just db-up-region-b` starts a second, independent Postgres (port `5433`) and
dev-mode Vault (port `8201`) from `compose.region-b.yml`, then runs `just vault-dev-init
http://localhost:8201` so that Vault has AppRole auth before `provision` needs it. Point
`CONTROL_DATABASE_URL`, `VAULT_ADDR` and `MESSGR_REGION` at it to run a second region beside the
default one. `just db-down-region-b` stops it.

== Producers

A *producer* is an upstream system — fraud alerts, statements, onboarding, and so on — allowed
to submit messages on behalf of a tenant. `messgr-control producer` registers, disables, and
lists producers for a tenant. Producer and tenant identity on the send path are resolved from
the client's mTLS certificate, never from the request body; `messgr::producer::resolve` is the
shared resolution layer, and `messgr-ingest` is the binary that terminates mTLS and calls it. See
the "Control-plane CLI" chapter for the full command reference.

== Dev PKI

`messgr-control dev-pki` issues test client certificates from a Vault-backed PKI secrets engine,
so producer mTLS resolution can be exercised locally without a real certificate authority. It
refuses to run outside a `dev` profile. See the "mTLS resolution and dev PKI" chapter for the
full walkthrough.
