= messgr-ingest: `POST /comms`

`messgr-ingest` (`T-011`) is the first end-to-end send path: it terminates mTLS itself, resolves
the client certificate to a producer via `resolve_producer` (see "mTLS resolution and dev PKI"),
resolves the customer and address to send to (see "Customer projection" in the control-plane CLI
chapter), and writes the ledger + outbox row in one transaction, encrypting the destination and
rendered template body under the customer's DEK (DESIGN.md §4.1-§4.3, §7, §11). The request body
identifies the customer one of three ways -- exactly one of `customer_id`, `external_id` +
`external_id_system` together, or neither (resolve by `destination` alone) -- any other
combination is rejected (`422`). Quotas (§5.1) are still unbuilt; suppression and consent (§5)
are now enforced, but at dispatch time, not here -- gates run at send time, never at ingest
(§6.2), so this process never checks either -- see "messgr-dispatcher" (`T-038`, `T-037`).
`class = "auth"` is rejected outright (`422`) -- OTP has its own path (`sms-sender`/`otp-api`,
`T-047`), never this one.

The request body also takes two optional RFC3339 timestamps, both absolute UTC (`T-040`):
`scheduled_for` delays claim eligibility until that time instead of immediately (a past value
collapses to "send immediately", the same as omitting it); `expires_at` is written straight
through to the outbox and checked by the dispatcher's Expiry gate the first time the row would
be claimed (§5), never rejected here even if already in the past -- one code path handles both
"expired before dispatch" and "expired while queued". A `scheduled_for` further out than the
tenant's `schedule_horizon_days` (`messgr-control tenant-config show`, default 90) is rejected
(`422`), alongside the other validation `422`s above -- `expires_at` carries no such horizon.

`T-016` adds the first two ingest-side rejections ahead of the full gate chain: a client
certificate belonging to a tenant whose `tenant.status` isn't `active` (suspended or
offboarding) gets `403`, distinct from an unregistered or disabled producer certificate's own
`403`; and a currently-engaged kill switch matching this request's channel, producer, or
campaign gets `503` (temporary -- the switch may release at any moment), checked against a
poll-refreshed in-process cache rather than `kill_switch` directly, since this process connects
through PgBouncer transaction mode, where `LISTEN` never fires (DESIGN.md §2.3, §5.2). See
"Kill switches" for how an operator engages/releases one.

Requires four env vars, no defaults (`.env.example`): `INGEST_LISTEN_ADDR` (default
`0.0.0.0:8443` if unset), `INGEST_TLS_CERT_FILE`, `INGEST_TLS_KEY_FILE`,
`INGEST_TLS_CLIENT_CA_FILE`. A fifth, `INGEST_HEALTH_LISTEN_ADDR` (default `0.0.0.0:8080`,
`T-032`), binds a second, plain (non-TLS) listener serving only `GET /healthz` -- a bare `200`
for an orchestrator/LB liveness probe, no client certificate needed. Locally, mint a server
identity with a DNS SAN (unlike a producer's
own client certificate, a server's certificate _is_ hostname-checked by whatever connects to
it):

[source,bash]
----
just dev-pki-bootstrap
just dev-pki-issue-server-cert messgr-ingest.internal /tmp/ingest-cert   # writes cert.pem, key.pem, ca.pem

INGEST_TLS_CERT_FILE=/tmp/ingest-cert/cert.pem \
INGEST_TLS_KEY_FILE=/tmp/ingest-cert/key.pem \
INGEST_TLS_CLIENT_CA_FILE=/tmp/ingest-cert/ca.pem \
just ingest-run
----

Then, with a tenant provisioned, configured, and a producer registered (see the control-plane CLI
chapter) and a client certificate issued for it via `just dev-pki-issue-cert` (no `--server` -- a
producer's certificate is never hostname-checked):

[source,bash]
----
curl -sk --cert /tmp/producer-cert/cert.pem --key /tmp/producer-cert/key.pem \
  --cacert /tmp/ingest-cert/ca.pem --resolve messgr-ingest.internal:8443:127.0.0.1 \
  -H "Idempotency-Key: demo-1" -H "Content-Type: application/json" \
  -d '{"customer_id":"<uuid>","destination":"+15550100","channel":"sms","class":"transactional","template_id":"balance-alert","template_version":1,"variables":{"name":"Jordan","balance":"100.00"}}' \
  https://messgr-ingest.internal:8443/comms
----

Or identify the customer by an upstream system's own id instead of a `messgr` `customer_id`:

[source,bash]
----
curl -sk --cert /tmp/producer-cert/cert.pem --key /tmp/producer-cert/key.pem \
  --cacert /tmp/ingest-cert/ca.pem --resolve messgr-ingest.internal:8443:127.0.0.1 \
  -H "Idempotency-Key: demo-2" -H "Content-Type: application/json" \
  -d '{"external_id":"core-banking-12345","external_id_system":"core_banking","destination":"+15550100","channel":"sms","class":"transactional","template_id":"balance-alert","template_version":1,"variables":{"name":"Jordan","balance":"100.00"}}' \
  https://messgr-ingest.internal:8443/comms
----

Returns `201` with a `comms_request_id` on the first call; repeating it with the same
`Idempotency-Key` returns `200` with the same id rather than sending twice. The one error case
specific to resolution is an invalid combination of `customer_id`/`external_id`/
`external_id_system`, which is `422` -- resolution itself never rejects a send, even when a
`destination` is already active under a _different_ customer than the one the request named; it
resolves to that other customer instead (see "Customer projection" in the control-plane CLI
chapter). Once `messgr-dispatcher` is running against this tenant and channel, the row is picked
up and `final_status` moves to `sent` or `failed`.

== `DELETE /comms/{id}`

Cancels a not-yet-sent message (`T-041`, DESIGN.md §6.2). Scoped to the producer that created
the row -- a request against another producer's id is indistinguishable from an unknown id
(`404`, never `403`), so the endpoint leaks nothing about whether an id belongs to another
producer:

[source,bash]
----
curl -sk --cert /tmp/producer-cert/cert.pem --key /tmp/producer-cert/key.pem \
  --cacert /tmp/ingest-cert/ca.pem --resolve messgr-ingest.internal:8443:127.0.0.1 \
  -X DELETE https://messgr-ingest.internal:8443/comms/<comms_request_id>
----

Returns `204` on success, idempotently -- a second `DELETE` on an already-cancelled row is still
`204`, not an error. `404` for an unknown id or one belonging to another producer. `409 Already
Sent` when the message already reached a terminal state other than `cancelled` -- it was already
sent, failed, expired, or suppressed, and that cannot be undone.

This call only _requests_ cancellation: `messgr-dispatcher` makes the final call at send time
(§6.2), re-reading `cancelled_at` immediately before it calls the provider, since a cancel can
arrive while the dispatcher already holds the row's lease. A `204` response here does not itself
guarantee the message never goes out -- if the dispatcher's send already started, cancellation
lost the race and the message sends; the ledger's `final_status` is the source of truth for what
actually happened, not this response.

`docker compose up -d` also starts a dev-mode Vault (`VAULT_ADDR=http://localhost:8200`,
`VAULT_TOKEN=messgr-dev-root-token`, both in `.env.example`) backing the `KeyStore` trait
(`src/keystore.rs`) that per-customer data-encryption keys go through (DESIGN.md §7.6).
`just vault-dev-init` is idempotent and only needs to run once per fresh Vault container -- it
enables the Transit secrets engine and creates the `messgr-dek` key that `tests/keystore.rs`
exercises, and now also enables the `approle` auth method that every tenant's own AppRole (one
role per tenant, inside this single shared backend) is created under. A dev-mode Vault is for
local development and CI only: `VaultKeyStore::connect` refuses to start against a non-TLS
`VAULT_ADDR` outside `MESSGR_PROFILE=dev`.
