= Kill switches

`T-016` builds the kill-switch mechanism from DESIGN.md §5.2: five scopes, hold-by-default with
an explicit discard option, engaged and released via a documented `psql` runbook against the
tenant database -- the operator-facing panel is a later build-order step (§14), so this page
_is_ the interface for now.

== Scopes

`kill_switch.scope` is one of `global`, `channel`, `producer`, `producer_channel`, or `campaign`.
`scope_key` carries the value that scope narrows to, and is `NULL` only for `global`:

[cols="1,2"]
|===
| scope | `scope_key`

| `global`
| `NULL`

| `channel`
| a channel name, e.g. `sms`

| `producer`
| a `producer_id` (uuid, as text)

| `producer_channel`
| `"<producer_id>:<channel>"` -- the one scope that needs two keys, packed into this single text
column (e.g. `"3fa85f64-5717-4562-b3fc-2c963f66afa6:sms"`)

| `campaign`
| a `campaign_id`
|===

== Engaging a switch

As of `T-049`, the admin panel's kill-switch console (`docs/user-manual/query-api.adoc`) is the
primary way to engage a switch -- it shows the blast radius before engaging and requires a
reason, the same as this runbook. This `psql` form is the documented fallback: it stays exact and
unchanged, since `auth_enabled` (below) and any panel-unreachable scope still need it.

[source,sql]
----
INSERT INTO kill_switch (id, scope, scope_key, on_queued, engaged_by, engaged_at, reason)
VALUES (gen_random_uuid(), 'producer', '3fa85f64-5717-4562-b3fc-2c963f66afa6', 'hold',
        'alice@example.com', now(), 'runaway campaign, investigating');
----

`on_queued` is `hold` (the default -- most incidents end in "resume") or `discard` (for the ones
that don't: a six-hour-old flash-sale blast firing after the sale ended is worse than never
sending it). The unique index on `(scope, COALESCE(scope_key, ''))` where `released_at IS NULL`
means only one switch can be active per exact `(scope, scope_key)` pair at a time -- a second
`INSERT` for the same pair while one is already active fails, rather than silently stacking.

Engaging does three things, within seconds: `messgr-ingest` starts rejecting new matching
requests (`503`, its own poll-refreshed cache, checked every few seconds -- `LISTEN` doesn't
reach it behind PgBouncer, §2.3); `messgr-dispatcher` stops claiming matching `outbox` rows
(excluded from the claim query's candidate set entirely, via its own cache -- refreshed
immediately on the `kill_switch` `NOTIFY`, with a 30-second poll fallback); and, only for
`on_queued = 'discard'`, every currently-matching held row is immediately written a `discarded`
terminal state.

A `producer`-scope switch stops that producer on every channel; `producer_channel` narrows to
one channel; `channel` stops every producer on that channel; `campaign` stops one campaign;
`global` stops everything (auth/OTP excepted -- see below, regardless of scope).

== Releasing a switch

As with engaging, the admin panel's kill-switch console is now the primary path to release a
switch. This `psql` form remains the documented fallback.

[source,sql]
----
UPDATE kill_switch
SET released_by = 'alice@example.com', released_at = now()
WHERE id = '<the switch's own id>' AND released_at IS NULL;
----

Release does not dump the whole backlog back onto the provider at once. `messgr-dispatcher`
ramps a `hold` switch's backlog back in at `tenant_config.kill_switch_release_rate` rows/second
(default 500; set with `messgr-control tenant-config set --kill-switch-release-rate <n> ...`),
per channel, until the backlog for that scope is empty. A held row whose `expires_at` has
already passed by the time it's drained is written `expired` rather than sent late (DESIGN.md
§6.2). `messgr-ingest` stops rejecting new matching requests immediately on release -- the ramp
is a dispatch-side concern about not overwhelming a provider with a backlog, not about blocking
new traffic.

== The auth kill switch (`auth_enabled`)

Auth/OTP shares no process with the dispatcher (AGENTS.md hard invariant 1, §3), so nothing
above reaches it -- a `global` kill switch does not stop customer login. Disabling auth is a
separate, tenant-scoped column in the *control* database, `tenant.auth_enabled`. As of `T-052`,
`messgr-sms-sender` is this column's reader: it polls the control database every 5 seconds and
fails *open* (auth stays enabled) on a read failure or a timeout, per the migration's own
mandate -- a control-database outage must never silently disable customer login. `messgr-otp`
(`T-056`, cloud, build-order step 19) polls the same way -- see "messgr-otp". The two-person approval DESIGN.md's Still-Open #9
asked about is, for now, an out-of-band human process this runbook records rather than a tool
enforces (decision 29): both approvers confirm to each other outside any tool, then one of them
runs both statements in the same transaction:

[source,sql]
----
BEGIN;
UPDATE tenant SET auth_enabled = false WHERE slug = 'acme';
INSERT INTO platform_audit (id, actor, action, tenant_id, detail, at)
VALUES (
    gen_random_uuid(), 'alice@example.com', 'auth_disabled',
    (SELECT id FROM tenant WHERE slug = 'acme'),
    '{"reason": "confirmed compromised OTP delivery channel", "approved_by": ["alice@example.com", "bob@example.com"]}',
    now()
);
COMMIT;
----

Re-enabling is the same shape, with `auth_enabled = true` and `action = 'auth_enabled'`. Run
these against the *control* database (`CONTROL_DATABASE_URL`), not the tenant database
`kill_switch` lives in.

== Platform-tier switches

In the cloud deployment, the provider has its own tier of kill switches (DESIGN.md §5.2 "Two
tiers in cloud", T-058), kept in the *control* database's `platform_kill_switch` table rather
than the tenant's `kill_switch` table. They are engaged and released only by provider staff --
with `messgr-control platform-kill-switch` or the platform console's kill-switches pane (see
`control-plane-cli.adoc`) -- never from the tenant's admin panel. There are two scopes:
`tenant` (one tenant, for abuse or non-payment) and `platform` (every tenant in the region, for a
platform-wide incident).

**A platform switch overrides the tenant's switches, never the reverse.** While one is engaged,
the tenant is treated exactly as if it had a `global` switch of its own with `on_queued = hold`:
`messgr-ingest` rejects every new request with `503` and scope `platform` (so a producer team can
tell the provider suspended the tenant, not their own ops team), and `messgr-dispatcher` claims
nothing for the tenant on any channel. Queued messages are always *held*, never discarded -- a
suspension does not touch the tenant's data. Nothing the tenant does with its own switches can
release it.

**Release ramps.** Releasing a platform switch drains the held backlog at the tenant's
`kill_switch_release_rate`, exactly like releasing a tenant switch; rows whose `expires_at` has
passed are written `expired`, not sent late. The ramp still honours every switch the *tenant*
has engaged: a campaign the tenant is holding stays held after the platform switch releases (and,
likewise, releasing a tenant switch never drains anything past a platform switch that is still
engaged). Every release drain -- tenant or platform -- skips rows another still-engaged switch
covers; those rows ramp in when that switch releases.

**Propagation.** Engaging or releasing sends `NOTIFY kill_switch` into each affected tenant's
own database (the channel `messgr-dispatcher` already listens on), so a dispatcher usually reacts
within seconds; its 30-second poll re-reads the control database regardless, so a missed or
failed notification delays a switch by at most one poll, never loses it. `messgr-ingest` does
not listen (PgBouncer, §2.3) and picks the switch up on its 5-second poll.

**Auth/OTP is not affected**, the same as for every other switch on this page. To stop a
tenant's OTP traffic as well, suspend the tenant from the platform console: suspension blocks
ingest and OTP by tenant status *and* engages a `tenant`-scope platform switch to hold the queued
backlog.

**What the tenant sees.** The tenant's admin panel shows an engaged platform switch as a
separate, clearly marked "Suspended by the platform operator -- contact support" block with the
time it took effect, above the tenant's own switches. It has no release control, and it never
shows the operator's reason, which stays provider-internal.

== What "held" means

A row under an active switch is left exactly as it was queued: not leased, not retried, not
gate-evaluated. It is not claimable at all until its switch releases and the drain ramp reaches
it (or, for `discard`, until it's terminal-written). There is no polling or spinning against it
in the meantime -- the dispatcher's claim query excludes it from its candidate set entirely for
as long as the switch (or, after release, the drain ramp) is active.
